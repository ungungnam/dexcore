# Public research page

`public_page/` holds the concise PUBLIC page of this project: what problem is studied, which
empirical observations motivate it, and which research direction follows. It is an "ongoing
research" page, not a paper page: observations → emerging hypothesis → research direction.

The detailed page under `docs/` is the INTERNAL page. It stays in the repository unchanged and is
the source of truth: every number, chart value and picture of the public page comes from it.

## How the two pages differ

| | Internal page (`docs/`) | Public page (`public_page/site/`) |
|---|---|---|
| Reader | the project itself | external researchers |
| Content | full reasoning, all evidence, failed experiments, diagnostics, current hypotheses | motivation, three observations, the research question |
| Length | long | 1,200 words at most (every chip, label, tile and table cell counted), plus four collapsed technical notes of at most 100 words |
| Method details | models, losses, training, the running experiment | none |
| Sources | report and file paths next to every figure | plain-words source labels only |
| Served on the web | no longer, once GitHub Pages points to `gh-pages` (see Deploy); previewed locally | yes, from the branch `gh-pages` |

The public page never links to the internal page, to `docs/`, to the evidence manifests or to the
code repository.

## Layout

```
public_page/
  README.md                       this file
  public_content_outline.md       the public story: sections, claims, figures, datasets
  public_evidence_manifest.json   claim -> internal source mapping. DEV ONLY, never shipped
  exposure_checklist.md           written by the check: one line per rule, PASS / FAIL + evidence
  build/
    public_figures.py             which internal figure each public chart is derived from, and its public labels
    public_claims.json            the claims of the page, their numbers and their internal evidence
    manual_checks.json            record of the checks that only a person can make (who, when, on which text)
    build_public.py               builds the chart data, copies the images, writes the manifest, runs the check
    check_public.py               exposure, traceability and self-containment checks over site/
    publish.sh                    publishes site/ as the branch gh-pages (see Deploy)
  site/                           THE SHIPPED STATIC SITE (self-contained, relative links only)
    index.html                    the page (written by hand)
    .nojekyll
    assets/css/style.css
    assets/js/charts.js           chart renderer (reads window.DEXCORE_FIGURES)
    assets/img/*.webp             three pictures, byte copies of internal renders under public names
    data/figures.js               chart data of the three charts, generated by build_public.py
```

## Build

```bash
source ~/miniconda3/etc/profile.d/conda.sh && conda activate dexmachina
PYTHONDONTWRITEBYTECODE=1 python public_page/build/build_public.py
```

The build needs no GPU and no network. It reads only files under `docs/` and `public_page/` (no
result folder), and writes only `site/data/figures.js`, the three pictures, the manifest and the
checklist; nothing under `docs/` is written. It

1. derives every public chart from one internal figure (`docs/data/figures.json`) as described in
   `build/public_figures.py`, writes `site/data/figures.js`, and compares every copied value with
   the internal figure again;
2. copies the three pictures from `docs/assets/img/` under their public names;
3. checks every entry of `build/public_claims.json` against the internal evidence and writes
   `public_evidence_manifest.json`;
4. runs `build/check_public.py` over `site/` and writes `exposure_checklist.md`.

It ends with `build_public: OK` and exit status 0 only when nothing failed. It FAILS when

- a displayed number is not the full-precision internal value at the displayed rounding;
- a referenced evidence key or figure value does not exist or differs (for a displayed number and
  for a supporting value of a claim that shows no digit);
- a figure asset is missing;
- a number in the text of the page does not lie inside the text of a claim that lists it and is
  not a listed structural number (a number moved to another sentence, quantity or dataset fails);
- a claim sentence, or one of its listed tile strings, is not on the page word for word;
- a number written in a chart title, label or note is not listed for that figure;
- a number typed into an axis label of a chart (the number of events of a kind) has no supporting
  value for that label and dataset, or its label is not in the panel of that dataset;
- a claim has no trace at all (no number, no supporting value, no evidence note).

The lines that start with `note:` are not failures: they list the numbers that the page shows only
as value labels of a chart.

The manifest and the checklist carry no time stamp: building twice gives the same bytes, so a
rebuild of committed files leaves `git status` clean.

## Check

The check runs as the last step of the build. It can also be run alone:

```bash
PYTHONDONTWRITEBYTECODE=1 python public_page/build/check_public.py
```

Read the result in `exposure_checklist.md`. Every rule must say PASS before the page is published.

## Preview locally


## Deploy

`site/` is a self-contained static folder: system fonts, no CDN, no request to any other host,
relative links only. It can be published from its own repository, from any static host, or as the
published folder of this repository.

The owner's decision (5 October 2026): the public page replaces the page served at the project's
GitHub Pages address. It is published from a `gh-pages` branch that holds ONLY the content of
`public_page/site/`; GitHub Pages source = branch `gh-pages`, folder `/`.

State: **deployed on 5 October 2026.** GitHub Pages serves the branch `gh-pages`; the internal page
under `docs/` is no longer served. Step 1 below is the command for every later change; steps 2 and 3
were needed once and are kept as a record.

**Step 1: publish the branch** (also the command that refreshes the page after every later change)

```bash
# on main, once the build says OK and public_page/ is committed:
bash public_page/build/publish.sh --push
```

`publish.sh` refuses to run when the current branch is not `main`, when `public_page/` has
uncommitted changes, when the full build does not end OK, or when the build changed a file (the
committed chart data, manifest or checklist was not a fresh build). It then builds one commit from
the tree of `HEAD:public_page/site` on top of the last published commit (the local branch
`gh-pages`, or `origin/gh-pages` in a checkout that has not published before) and pushes the
branch. The working tree and the current branch are not touched.

**Step 2: point GitHub Pages to the branch** (done once, on 5 October 2026; the branch must exist,
so this comes after step 1). Until this is done, GitHub Pages keeps serving `main:/docs`, the
internal page.

```bash
echo '{"source":{"branch":"gh-pages","path":"/"}}' | gh api -X PUT repos/<owner>/<repo>/pages --input -
gh api repos/<owner>/<repo>/pages --jq .source      # must print {"branch":"gh-pages","path":"/"}
```

**Step 3: request a build** (once, right after step 2). Changing the source does not rebuild the site
by itself: until a build runs, the old page stays online.

```bash
gh api -X POST repos/<owner>/<repo>/pages/builds
gh api repos/<owner>/<repo>/pages/builds/latest --jq '.status + " " + .commit'   # built <gh-pages commit>
```

Then open the project's GitHub Pages address and check that it shows the public page and that a file
of the internal page (for example `evidence_manifest.json`) answers 404. Later pushes of `gh-pages`
(step 1) rebuild the site by themselves.

Not part of the published branch: the internal page (`docs/`), `public_evidence_manifest.json`,
`exposure_checklist.md`, `public_content_outline.md`, this README and `build/`. Two things to keep
in mind:

- The internal page under `docs/` is no longer served on the web once GitHub Pages points to
  `gh-pages`, and is previewed locally. The repository itself stays public (owner's decision), so
  the files under `docs/` remain readable there; the public page does not link to them.
- Never publish `public_page/` as a whole: the manifest and the build files hold internal paths.

## Changing the page

1. Edit `site/index.html` and `site/assets/css/style.css`. Technical notes are
   `<details class="tech-note">`, at most 100 words each; the body text is at most 1,200 words.
   Words are counted with every inline element separated by a space, so each dataset chip, source
   label, stat tile and table cell counts as the words a reader sees (rules H01 and H02).
2. Every claim of the page has an entry in `build/public_claims.json`:
   - `public_claim` is the sentence as shown on the page, word for word, inside one text block;
   - `numbers[]` holds every number of that sentence: the displayed number, the dataset, the
     metric, the full-precision internal value and where it is in the internal evidence;
   - `shown[]` lists the exact strings that carry numbers of the claim outside its sentence (stat
     tiles such as `TACO 0.85 119 events`);
   - a number that the page shows only as a value label of a chart is marked `"where": "chart"`
     (the claim's `figure_asset` must then name the public chart that plots it);
   - `support[]` holds the values behind a claim that shows no digit ("unchanged", "no
     reduction"): same fields as a number, with `shown_as` instead of `displayed`;
   - a number that is typed into an axis label of a chart (`contact moves (119)`) needs a
     supporting value marked `"where": "chart"` whose `shown_as` is that label, word for word: the
     build compares the value with the internal evidence and checks that the label stands in the
     panel of that dataset;
   - `evidence_note` is free text for readers of the manifest (not machine-checked).
   A number of the page is accepted only inside the text of a claim that lists it, or inside a
   phrase of `structural_numbers` (sizes, counts, dates, thresholds; each with its reason).
3. A chart that needs another label, panel or series: edit `build/public_figures.py`. The file may
   hold no plotted number; values are copied from the internal figure by the build. Numbers written
   in a title, label or note of a chart are listed per figure in `chart_text_numbers` of the claims
   file.
4. A new or changed picture fails rule I02 until someone has looked at the text drawn in it and
   recorded its hash in `INSPECTED_IMAGES` of `build/check_public.py`.
5. Any change of the page text or of a chart title, label or note makes the manual text checks
   stale (rule M01). Read the page again as described under "Checked by people", then record the
   new digest, the date and your name in `build/manual_checks.json`; the failure message prints
   the digest, and so does `python public_page/build/check_public.py --pins`.
6. Run the build; fix every FAIL; look at the page at 1280 px and at 390 px.

## Final checklist

`exposure_checklist.md` is the record of the last build: one line per rule with PASS or FAIL, what
was scanned, and for a failure the file, line and text. The rules, in plain words:

Shipped files
- S01 Only the expected files are in `site/` (no manifest, checklist, source data, code or hidden file).
- S02 The chart data file holds public figures only (no source list, module or internal id).

Vocabulary of the internal work. Scanned: the page text (each block also with its inline tags read
as spaces), text attributes, comments, processing instructions, declarations and CDATA sections,
the raw HTML source, the strings of the chart data, CSS and scripts (comments, strings, code),
image metadata and file names. Words of the internal modelling work are also searched inside
identifiers (id and class values, attribute and element names, CSS selectors and custom
properties, script identifiers and object keys, file names).
- V01 No internal model, case or study code (also in lower case in what a reader sees).
- V02 The internal level names appear only inside the one technical note.
- V03 No identifier of the internal page (figure ids, evidence blocks, section names, render file names).
- V04 No internal symbol or code-like identifier, in the text or in id / class values.
- V05 No learned latent state or realization code, as a word, as a symbol (with or without an index) or inside an identifier.
- V06 No training recipe or architecture detail (supervision, losses and weights, sizes, architecture names, seeds, step / iteration / epoch counts, run dates, checkpoints).
- V07 No internal diagnostic, experiment or plan, and no to-do marker.
- V08 Cross-check: none of the internal page's figure ids, image names, evidence files or source paths appears.
- V09 No invisible character that could split a word (soft hyphen, zero-width characters, byte-order mark).

Paths and personal information
- P01 No server path or internal directory.
- P02 No file name of data, code, logs or documents, and no hash.
- P03 No host, user or account name, no personal name or affiliation, no author meta element, no IP address, and no e-mail address other than the contact address. Some names are held as digests only, so that this public repository does not spell them out.

Self-containment and links
- N01 Nothing is loaded from the network, and no script builds an element or an address that could.
- N02 Every referenced local file and anchor exists; references are relative and stay inside the site.
- N03 Outgoing links go only to the allowlisted public pages (datasets, cited work, the contact line).
- N04 No link or reference to the internal page, `docs/`, the evidence manifests or the code repository.

Wording and positioning
- W01 None of: prove, solve, final method, state-of-the-art, human intent, noise, true task functionality, optimal, necessary, disentangled, our method, outperform, we show, best.
- W02 "Null-space" at most once, as "null-space-like", inside an element marked as intuition (the page does not use it).
- W03 The page is labelled "Ongoing research" and "Work in progress".

Length, structure and accessibility
- H01 Body text of at most 1,200 words. Counted on the visible text outside the technical notes, with every inline element separated by a space (each chip, source label, stat tile and table cell counts as its own words); alt texts are not counted. The line of this rule in the checklist also gives the count of the running prose alone.
- H02 Each technical note of at most 100 words (its summary line included; same count).
- H03 Exactly one h1; heading levels do not skip.
- H04 Every image has alt text; every inline SVG has a role and a label.
- H05 Every chart placeholder names a figure of the data file, every figure of the data file is shown, and the data is loaded before the renderer.

Images and traceability
- I01 Images carry no EXIF / XMP block and no text or comment chunk.
- I02 Every image is a version whose drawn text was inspected by eye.
- T01 Every number in the text of the page lies inside the text of a claim that lists it, or is a listed structural number.
- T02 Every claim is on the page word for word, every displayed number is in its claim's text or plotted in the chart the claim names, and every number typed into a chart label that has a supporting value stands in the panel of its dataset.
- T03 Every number written in a title, label or note of the chart data is listed for that figure in the claims file, and a number typed into an axis label has a supporting value for that label and dataset.

Checked by people (rule M01)
- M01 The checks below are recorded in `build/manual_checks.json` with a date and the name of who made them, and the two text checks were made on the text as it is now.

## Checked by people, not by the script

The vocabulary rules find listed words, codes, names and paths. They cannot recognise a
description of the internal work in other words, and they cannot read a picture. Four checks are
therefore made by a reader and recorded in `build/manual_checks.json`, each with the date and the
name of who made it:

- `page-text`: the whole page text and the chart titles, labels and notes were read: a reader
  leaves with the four take-aways and nothing of the internal modelling work, no plan, no to-do;
- `direction-wording`: the section "Current research direction" says only what the brief allows;
- `image-text`: the text drawn inside the three pictures holds no internal code, name or path;
- `render`: the page at 1280 px and at 390 px: figures legible, no horizontal page scroll.

The two text checks are pinned to a digest of the text that was read, so every later change of
the text fails rule M01 until the text has been read again.

The records of 5 October 2026 were made by agents. The two text checks and the render check were
made again by the agent that tightened the page after its audit (the text was shortened to the
limits above); the picture check is the one of the repair before it (the three pictures have not
changed since: rule I02 pins them). They are a first reading, not the owner's sign-off: the final
reading by the orchestrating session and by the owner is still due. Before publishing, the owner
reads the page, looks at the pictures and at the page in a browser, and puts their own name and
date into the records.
